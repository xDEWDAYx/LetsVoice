## 结论摘要

这台 M2 Pro 16GB 可以完成 SpeakSpace Local 的标准全套硬件工作负载。首次严格模式全套
测试中的 TTS、TTS 连续运行内存、TTS 长文本、LLM 和 STT 五个阶段全部为 `ok`，总耗时
**1 小时 21 分 30.7 秒**。随后按最新标准清单单独重跑 STT，将覆盖范围从 4 个模型补齐为
**16 个模型、896 次计时**；重跑耗时 **40 分 33.9 秒**，同样没有失败。

| 结论项     | 结论                                                          | 建议                                                             |
| ---------- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| 整机可用性 | 标准全套硬件基准通过                                          | 可用于本地开发和功能验证                                         |
| TTS        | 三个模型均完成 36 条 × 3 次合成，失败为 0                     | 只看本机性能与内存，优先把 MeloTTS 作为默认候选                  |
| MOSS-TTS   | 本机最快，但长文本峰值达到 5843.3 MiB，内存随文本长度放大明显 | 仅作为高性能候选；上线前必须分段、设内存保护并做长时间稳定性测试 |
| LLM        | 五个模型均完成，均报告 100% GPU offload                       | 只看速度，Qwen2.5 1.5B 最快；最终模型仍应结合质量评测选择        |
| STT        | 16 个 Whisper 模型共 896 次计时，失败为 0，全部快于实时       | `small` 已有较大实时余量；大模型和 Turbo 系列也都可本地实时运行  |
| 质量结论   | 本轮 `with_accuracy=false`                                    | 不能据此判断 TTS 音质、LLM 答案质量或 STT 准确率                 |

因此，这次测试回答的是“这台机器跑不跑得动、速度和资源开销怎样”，不是“哪个模型的
输出质量最好”。性能上不存在阻断 SpeakSpace Local 开发的硬件问题；主要风险集中在
MOSS-TTS 的长文本内存占用，以及 MeloTTS、MOSS-TTS 连续运行探针显示的缓慢增长。

## TTS：MeloTTS 最均衡，MOSS-TTS 最快但内存风险最大

RTF（实时因子）= 合成耗时 ÷ 音频时长，越低越快；RTF 小于 1 表示合成速度快于实时播放。
每个模型使用同一批 36 条中英及中英混合文本，每条重复 3 次。

| 模型                    |   P50 RTF |   P95 RTF |       峰值 RSS | 加载 + 首次合成 | 失败 |
| ----------------------- | --------: | --------: | -------------: | --------------: | ---: |
| Kokoro Multi-Lang v1.0  |     0.952 |     1.167 |     1195.7 MiB |         8.49 秒 | 0/36 |
| MeloTTS Chinese-English |     0.761 |     0.801 |      895.5 MiB |         4.51 秒 | 0/36 |
| MOSS-TTS-Nano 100M      | **0.344** | **0.485** | **5637.0 MiB** |         6.70 秒 | 0/36 |

- **MeloTTS 是性能与内存的最佳平衡候选。** 它的 P95 RTF 仍为 0.801，峰值 RSS 是三个模型
  中最低的 895.5 MiB。这里的“最佳”只指本轮速度和内存，不包含听感。
- **MOSS-TTS 速度优势明显，但不适合在 16GB 机器上无约束处理长文本。** 它的中位 RTF
  约为 MeloTTS 的 45%，但常规语料峰值 RSS 已达到 5.5 GiB 左右。
- **Kokoro 可以运行，但尾部性能余量最小。** P50 仍快于实时，P95 为 1.167，说明慢样本
  可能低于实时合成速度；同时它的峰值内存也高于 MeloTTS。
- 三个模型的输出均未发现非有限采样或削波，脚本记录的合成失败均为 0。执行期间
  MeloTTS 对冒号类字符出现过 OOV 警告，但未形成失败；这属于需补充发音听测的运行观察，
  不是本轮已经证明的音质缺陷。

### 连续运行与长文本内存

| 模型     |  基线 RSS | 连续运行末次 RSS | 释放引擎后 RSS | 后半程每次增长 | 脚本判定    |
| -------- | --------: | ---------------: | -------------: | -------------: | ----------- |
| Kokoro   | 181.5 MiB |        923.3 MiB |      923.3 MiB |       0.04 MiB | stable      |
| MeloTTS  | 173.7 MiB |        677.9 MiB |      677.9 MiB |       1.94 MiB | slow-growth |
| MOSS-TTS | 172.4 MiB |       5162.5 MiB |     4179.0 MiB |       4.05 MiB | slow-growth |

| 模型     |   文本长度范围 | 短文本峰值 | 长文本峰值 |  峰值放大 |
| -------- | -------------: | ---------: | ---------: | --------: |
| Kokoro   | 24 → 1196 字符 |  911.4 MiB | 1084.2 MiB |     1.19× |
| MeloTTS  | 24 → 1196 字符 |  634.9 MiB |  791.4 MiB |     1.25× |
| MOSS-TTS | 24 → 1196 字符 | 1532.5 MiB | 5843.3 MiB | **3.81×** |

这些结果支持以下工程措施：

1. 默认优先验证 MeloTTS，并对 OOV 标点做文本规范化和听测。
2. MOSS-TTS 必须限制单段字符数、串行合成、监控进程 RSS，并在压力测试中验证释放策略。
3. 不把 `dispose` 后 RSS 没有立即回到基线直接等同于内存泄漏；运行时和系统分配器可能保留
   已分配内存，但 `slow-growth` 判定仍需要更长时间、更高迭代次数的回归测试来排除累积风险。

证据：三个 `tts-*.json`、`tts-memory-*.json` 和 `tts-length-*.json` 均位于
[`results/machines/m2-pro-16gb/`](./results/machines/m2-pro-16gb/)。

## LLM：五个模型都能完整卸载，Qwen2.5 1.5B 吞吐最高

| 模型                  |          中位吞吐 | GPU offload | 运行错误 |
| --------------------- | ----------------: | ----------: | -------: |
| Qwen2.5 1.5B Instruct | **71.9 tokens/s** |        100% |        0 |
| Qwen2.5 3B Instruct   |     43.9 tokens/s |        100% |        0 |
| Phi-4 Mini            |     37.0 tokens/s |        100% |        0 |
| Ministral 3 3B Q4_K_M |     35.3 tokens/s |        100% |        0 |
| Granite 4 Micro-H     |     30.2 tokens/s |        100% |        0 |

Qwen2.5 1.5B 在这组短、中、长提示词探针中吞吐最高，约为最慢模型 Granite 的 2.38 倍。
所有模型均由 Ollama 报告 100% GPU offload，说明没有观察到模型层回落 CPU 的情况。

Apple Silicon 使用统一内存，本机也没有 `nvidia-smi`，所以独立显存容量和 NVIDIA 式显存
采样字段为空。100% offload 只说明 Ollama 报告的模型层卸载状态，不能把它解读为“显存占用为
零”或“统一内存没有压力”。

本轮不评价回答质量。最终模型选择应把这些速度数据与
[`llm-model-sweep.md`](./llm-model-sweep.md) 的能力评测一起看，不能只按 tokens/s 决定。

证据：[`llm-runtime.json`](./results/machines/m2-pro-16gb/llm-runtime.json)。

## 跨机器对比：M2 的 TTS/STT 有优势点，LLM 吞吐落后于 NVIDIA 机器

仓库当前收集了四台机器，但另外三台各有部分阶段或模型数据。因此下面只比较双方都有的同一模型
或同一工作负载，不把缺失项当成 0，也不宣称这是全面的硬件排名。

### 与 RTX 3090 台式机比较 TTS

| 模型     | RTX 3090 台式机 P50 RTF | M2 Pro P50 RTF | M2 观察结果              |
| -------- | ----------------------: | -------------: | ------------------------ |
| Kokoro   |                   0.744 |          0.952 | RTF 高 28.0%，即更慢     |
| MeloTTS  |                   0.556 |          0.761 | RTF 高 36.9%，即更慢     |
| MOSS-TTS |                   0.634 |          0.344 | RTF 低 45.7%，约快 1.84× |

MOSS-TTS 在两个平台的内存差异很大：台式机归档结果峰值为 19082.8 MiB，M2 为
5637.0 MiB。这个差异说明跨平台运行时行为不能简单概括为“模型内存跨机器基本不变”；在
补做版本对齐和重复测试前，不把它解释为硬件本身的确定优势。

### 与 RTX 3060 笔记本比较 LLM

相同五个模型上，RTX 3060 笔记本的中位吞吐约为 M2 Pro 的 **1.08× 至 1.69×**；RTX 3090
台式机仅有 Qwen2.5 3B 可比数据，其吞吐约为 M2 Pro 的 **5.25×**。这符合本轮数据中
NVIDIA 独显机器更适合追求 LLM 最高吞吐的结论，但不代表 M2 上的 30.2–71.9 tokens/s
不可用。

### 与 RTX 3060 笔记本比较 STT

M2 Pro 与 `desktop-qg1ej01` 共有 13 个可比 Whisper 模型。M2 在这 13 项上的平均 RTF
全部更低：速度优势从 `tiny.en` 的 **2.00×** 到 `large-v3-turbo-q5_0` 的 **8.51×**。
这说明本轮 whisper.cpp CPU 工作负载在 M2 Pro 上有一致优势，但仍不能把该结论外推到
不同 STT 运行时、准确率模式或未对齐的软件版本。

完整数字和机器配置见自动生成的
[`cross-machine-benchmark.md`](./cross-machine-benchmark.md)。

## 风险、缺口与下一步

| 优先级 | 风险或缺口                                          | 建议动作                                                         | 完成标准                                               |
| ------ | --------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------ |
| P0     | MOSS-TTS 长文本峰值 5.7 GiB，且随文本长度放大 3.81× | 加入分段上限、串行队列和 RSS 保护；运行 1 小时以上压力测试       | 无 OOM，RSS 达到平台后不再持续增长，取消和恢复路径可用 |
| P1     | MeloTTS 与 MOSS-TTS 连续运行判定为 slow-growth      | 增加 100 次以上循环和多轮加载/释放测试                           | 能区分缓存、分配器保留和真实泄漏，并建立回归阈值       |

| P2     | M2 只有一次完整运行                                 | 在冷机和热机各重复至少 3 次，记录温度与功耗条件                  | 给出方差或置信区间，排除偶然波动                       |

## 可复现方法

在仓库根目录双击 `一键跨机硬件测速-Mac.command`，或在终端运行：

```bash
./一键跨机硬件测速-Mac.command --machine m2-pro-16gb
```

Mac 一键脚本会调用：

```bash
npm run bench -- --machine m2-pro-16gb --strict
```

本次只补跑 STT 全模型，使用：

```bash
npm run bench -- --machine m2-pro-16gb --only stt --strict --no-stt-fetch
```

随后可在主控机重新生成跨机器总表：

```bash
npm run bench:aggregate
```

本轮原始结果目录：
[`docs/testing/results/machines/m2-pro-16gb/`](./results/machines/m2-pro-16gb/)。其中：

- `run-manifest.json`：阶段状态、耗时、准确率开关和文件清单；
- `machine.json`：机器指纹；
- `tts-*.json`：TTS 速度、失败数和信号有效性；
- `tts-memory-*.json`：连续运行 RSS；
- `tts-length-*.json`：文本长度与峰值内存；
- `llm-runtime.json`：LLM 吞吐与卸载比例；
- `stt-human-speed.json`：STT 速度与失败数。

## 结论边界

这份报告可以证明：在记录的软硬件环境和测试语料下，M2 Pro 16GB 完成了标准全套硬件基准，
三个 TTS、五个 LLM 和 16 个 Whisper 都能运行，并获得了上述速度与内存数据。

它不能证明：

- TTS 的主观音质或发音正确率；
- LLM 的任务完成质量、安全性或幻觉率；
- STT 在更多说话人、口音、噪声环境中的准确率；
- 长时间日常使用一定不会发生内存泄漏；
- 单次运行能代表所有 M2 Pro 16GB 机器或所有系统版本；
- 跨平台差异完全来自硬件，因为 Node.js、驱动、运行时和系统版本并未完全对齐。
