# Agent 评测语料：80 条笔记 / 90 个任务

机器可读源文件：[agent-eval-corpus.ts](../../../scripts/benchmark/agent-eval-corpus.ts)（笔记 + 第一批任务）、
[agent-eval-tasks-v2.ts](../../../scripts/benchmark/agent-eval-tasks-v2.ts)（第二批任务，扩大保留集用）

这份语料测的是 Agent 能不能在一个**固定的笔记知识库**里，针对一条指令找到对的笔记、
读出对的事实、给出对的回答——不测生成能力，测的是检索、事实核对和范围约束。

同一份语料还喂给了一份独立评测：[retrieval-eval.md](../retrieval-eval.md) 复用这里 90 个任务里
`relevantNoteKeys` 不为空的 24 个（retrieval 场景 + ambiguous 场景），跳过 LLM，直接拿
`instruction` 当查询词测混合检索算法本身，跟 Agent 报告里"LLM 会不会用检索"的数字分开看。

## 4 个工作区，80 条笔记

| 工作区 | key | 说明 |
| --- | --- | --- |
| 产品研发 | `product` | Atlas、Phoenix 等项目——**故意放了两个相似项目**，测 Agent 会不会张冠李戴 |
| 客户项目 | `clients` | Northwind 等客户续约、风险评审 |
| 个人生活 | `personal` | 酒店预订、日常安排 |
| 研究资料 | `research` | 参考资料类笔记 |

笔记分两类：

- **30 条核心笔记**——真正携带事实的笔记，中/英/中英混合都有，同一项目的多条笔记之间
  常常有互相印证或互相矛盾的细节（比如 Atlas 桌面版和 Atlas mobile beta 的两个不同日期），
  专门测 Agent 会不会把两条弄混。
- **50 条生成干扰笔记**——不含任何 Atlas / Northwind / Helios / LFP 的正式结论，
  内容是无关的归档条目，长度按 220 / 600 / 1200 / 2200 字符四档循环生成，
  用来模拟真实知识库里"无关但看着像"的长笔记，测检索会不会被干扰项拖偏。

笔记总数固定为 80，写进了源文件的运行时断言里——语料被意外改动会直接抛错，
不会出现"数字对不上但没人发现"的情况。

## 90 个任务，7 种场景

| 场景 | 条数 | 测什么 |
| --- | --- | --- |
| retrieval（检索） | 16 | 能不能从 80 条里找到相关的那一条 / 几条 |
| cross-note（跨笔记） | 15 | 答案分散在不止一条笔记里，需要综合 |
| single-note（单笔记） | 14 | 答案就在一条笔记里，测基本的读取与事实提取 |
| scope（范围约束） | 12 | 只能用给定工作区/笔记范围内的信息回答，不能用范围外的 |
| unanswerable（不可回答） | 12 | 知识库里没有答案，测 Agent 会不会瞎编而不是说"查不到" |
| ambiguous（歧义） | 11 | 指令本身有歧义，测 Agent 该不该先澄清而不是自己猜一个 |
| todo-tool（待办工具） | 10 | 需要调用待办相关工具而不是纯问答 |

## 开发集 45 / 保留集 45

跟待办提取语料一样的拆分逻辑：dev 用于选定脚手架方案，holdout 只在方案定稿后验收一次。

这个拆分本身有一段教训：最早的开发集只有 8 条，脚手架实验在上面做出「50% → 100%」的提升，
换到保留集直接掉到 36.7%——8 条样本上的"提升"其实是在拟合噪声。后来把任务总数从 28 条
扩到 90 条（开发集 8→45），源文件里专门写了运行时断言 `dev 少于 40 条就抛错`，
就是不想再犯同一个错误。

## 示例任务

**single-01 · single-note**
> Atlas 桌面版什么时候发布，批准预算是多少？

评分标准（`requiredFacts`，答案必须包含以下事实的至少一种写法）：
- 日期：`2026年10月18日` / `2026-10-18` / `10月18日`
- 预算：`48万元` / `48 万元` / `480,000` / `480000`

`forbiddenFacts`（一旦出现就判错，通常是来自相似项目 Phoenix 的干扰数字）：`72万元`、`2026年11月6日`。

这种"必需事实 + 禁止事实"的判分方式是可复核的严格规则判分，不依赖 LLM Judge 的主观打分，
详见 [agent-eval-scoring.ts](../../../scripts/benchmark/agent-eval-scoring.ts)。

## 已知局限

- 不是公开数据集，笔记内容和任务都是针对这个产品的场景手工构造。
- 90 个任务的场景分布是构造者主观决定的，不代表真实用户问题的分布。
- 干扰笔记的"无关性"由内容规则保证（不含四个项目名的正式结论），不是随机采样的真实笔记。
