## 一、把 ASR 错误引入待办提取的输入 —— 最值得做

**当前评测喂给模型的是干净文本，真实链路拿到的是带识别错误的转写结果。**
这是现有数字与真实体验之间最大的一条缝：报告里 90.2% 的 F1 是在理想输入上取得的。

做法（工具链已经齐了，成本很低）：把 54 条语料用 TTS 合成 → 用 whisper 转写回来 →
拿转写结果当输入重跑 `bench:todo`，对比干净输入掉多少。

`tts-asr-eval.ts` 已经实现了「合成 → 转写 → 算 CER」的全部环节，改造成本主要是把
转写文本接回待办语料。**这个数字比再堆多少测试都更能说明产品的真实水平。**

## 二、Agent 仍未达可用水平

五个模型都跑过完整 90 任务语料（开发集 45 / 保留集 45）之后，保留集上最好的是
`granite4:micro-h` 60.0%，其次 `ministral-3` 53.3%，**没有一个接近可用**。已知的三个失败模式：

- 该澄清时自行猜一个
- 该说「查不到」时硬答
- 只看搜索预览，不打开完整笔记核对——检索本身其实很准（见 [retrieval-eval.md](./retrieval-eval.md)，
  跳过 LLM 直接测同一套检索算法，Recall@8 达 98.6%），瓶颈几乎全在 LLM 那一端：不调用
  `search_notes`，或者读了搜索预览就直接作答、不再打开完整笔记核对。

脚手架实验最早只在 `granite4` 上拿到 +11.1（预载证据），当时**没有做保留集验收**；
现在补了一次真实对照——`qwen2.5:3b-instruct` 套用脚手架（预载检索+读取前2条、歧义路由、
证据核查）后，保留集完成率从基线的 35.6% 提到 40.0%，约 +4.4 个百分点，远小于当初
dev-only 测出的 +11.1，且 dev（60.0%）与 holdout（40.0%）之间仍有 20 个百分点的差距，
说明脚手架本身也需要按模型分别做保留集验收，不能只测一个模型就当结论。
继续做之前要注意：这个项目里已经四次出现「同一手段在不同模型上效果相反」，见下方「四个坑」。

## 三、STT 真人评测已有第一批数据，但只有单一说话人

[stt-human-eval.md](./stt-human-eval.md) 已经用真人朗读（不是合成语音回转录）测出了
tiny/base/small/large-v1 四档 whisper 模型的 CER、噪音鲁棒性、内容覆盖率。

剩下的缺口：
- **只有一位中文母语者。** 换口音、换母语背景，结果会不一样，尤其英文那部分。
  [stt-recording-protocol.md](./stt-recording-protocol.md) 里的 D 段（换人朗读）就是为这个留的，
  目前没人做。
- **录音不是走应用自己的采集路径**，是手机自带 App 录的，跟真实麦克风输入链路有差距。
- 退而求其次也可以补公开数据集（AISHELL-1 test、LibriSpeech test-clean）作为交叉验证，
  但要在报告里写清楚许可与场景差异。

## 四、TTS 音质只有代理指标

108 个 WAV 样本已经生成好（路径见 TTS 报告末尾）。需要 3–5 人双盲、随机顺序，
按自然度、清晰度、发音准确性、中英切换四个维度五分制打分，算 MOS 与评分者间一致性。

## 五、Agent 的 LLM Judge 未经人类校准

报告目前引用的是可复核的严格规则判分，Judge 指标仅作参考。
`agent-eval-human-review.json` 已生成，全部任务里分层抽 10–12 条由真人标注即可得到有意义的 κ。

**注意**：不能用另一个大模型代替人类标注。κ 的前提是评分者独立、且一方是我们真正在意的
判断基准；用模型顶替得到的只是模型间一致率，回答不了「Judge 可不可信」。

## 六、只测了一台机器的硬件基准

Windows 这一轮是 i9-12900H / RTX 3060 / 40 GiB。跨机器入口已经建好，
在别的机器上跑 `npm run bench -- --machine <标签>` 即可积累对比数据，
见 [multi-machine-benchmark-guide.md](./multi-machine-benchmark-guide.md)。

## 七、检索质量评测只测了"查询词写得好"的情况

[retrieval-eval.md](./retrieval-eval.md) 用任务自带的 instruction 原文当查询词，比真实用户的
口语化提问更规整。真实查询词下的检索质量可能更低，这个差距目前没有量化——想知道有多大，
需要额外收集一批口语化改写的查询词，或者直接看 Agent 报告里"LLM 自己拼查询词"那组数字
（已经在检索报告里做了对照，但那组还额外混了"LLM 会不会决定去搜索"这个变量）。
另外目前只测了 bge-m3 一个 embedding 模型，没有跟其他本地可用的模型比较过。

## 做任何一项之前必须知道的四件事

这四条都真实发生过，每一条都产出过「看起来很有说服力但是错的」结论：

1. **并行毁数据。** 并行跑一次 `tsc`，Kokoro 的 RTF 从 0.79 变成 4.4。
2. **指标定义本身会错。** 内存判据第一版用首尾差，得出「Kokoro 缓慢增长、MOSS 累积」——
   两个都是错的；换成同段文本内的最小二乘斜率后是「两个稳定、MOSS 震荡」。
3. **小开发集会骗人。** Agent 脚手架在 8 条开发集上「50% → 100%」，保留集上掉到 36.7%；
   扩到 45 条后那些提升全部消失。**在小样本上做选择是在拟合噪声。**
4. **结果文件会静默覆盖。** 同名输出被后一轮冲掉，等要做前后对比时才发现数据没了。
   现在文件名都带模型、变体、脚手架、子集，机器结果按机器分目录 —— 新增实验维度时记得沿用。
5. **语料扩容之后，旧结果不会自己失效。** Agent 任务语料从 28 条扩到 90 条之后，
   `llm-model-sweep.md` 的 Agent 数字和旗舰版 `agent-end-to-end-eval.md` 分别停在了扩容前的
   28 条和扩容后但只跑了开发集（保留集从未跑过）——两份报告互相矛盾了一段时间都没人发现，
   因为每份单独看都"看起来正常"。图表和报告里所有「N 个任务」「dev X / holdout Y」这类数字
   现在都改成从结果 JSON 动态读取，不再手写字面量，就是为了不再需要「记得手动改」这一步。

## 工程约定

- 新脚本放 `scripts/benchmark/`，接进 `package.json`
- 注释用中文，解释**为什么**，不要复述代码在做什么
- 提交前过 `npm run lint` 和 `npx tsc --noEmit -p tsconfig.json`
- `scripts/benchmark/` 下的文件需要文件级 `/* eslint-disable no-await-in-loop, no-continue, no-restricted-syntax */`
- 图表用 `chart-svg.ts` 这个无依赖 SVG 模块，不要引图表库
- 评测要走应用真实代码路径（TTS 走 `TTSEngine`、Agent 走真实 `AgentOrchestrator`），
  **不要为了评测改生产代码** —— 脚手架实验全部通过已有注入点实现，生产链路一行未动
- **选择只在开发集做，保留集冻结**；报告里必须写明「这些数据不能证明什么」
- 新增测试集时，机器可读源文件放 `scripts/benchmark/`，人类可读说明放
  [datasets/](./datasets/README.md)，不要把测试集内容直接写进叙述性文档里
