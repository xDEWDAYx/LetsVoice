3. 【智能体】检索范围被收窄到单个工作区，手动关联的笔记完全没被使用
------------------------------------------------------------------------
问题：
  - 开启智能体模式后，必须先在左侧笔记库选中一条笔记才能提问。
  - 助理只能在选中笔记所属的那一个工作区里检索，跨工作区的相关笔记
    永远找不到。

原因：
  - StudioChatPanel 的 hasContext 要求必须挂上笔记或工作区，否则输入框
    与发送键直接 disabled；智能体模式同样受这个限制。
  - StudioPage 的 agentWorkspaceId 依次取「挂上的工作区 → 挂上笔记所属
    工作区 → 当前选中笔记的工作区」，再传给 Agent，检索被锁死在单个
    工作区（AgentNoteToolSupport.listScopedAgentNotes）。
  - 智能体模式下 linkedNotes 只被用来推断工作区 ID，笔记本身从未进入
    上下文，等于「手动指定」实际不起作用。

现在：
  - 智能体模式一律传 workspaceId: null，主进程退化为 findAll()，语义
    检索同样不限定工作区，检索覆盖全部笔记。
  - hasContext 增加 agentMode 短路，不挂任何东西也能直接提问。
  - 新增 linkedNoteIds 贯穿 AgentRunRequest → AgentContext；AgentInput
    负责清洗（丢弃非法 ID 而不是整次请求失败，上限 8 条）。
  - 挂上的笔记在 search_notes 结果里以 match: "linked" 置顶插入，检索
    没命中也不会丢失；系统提示同时说明这些是用户指定的额外线索，找别的
    内容仍要搜全库。
  - search_notes 的工具描述与系统提示改为明示「覆盖用户全部笔记」，
    避免模型自行认定某条笔记够不着。

5. 【仪表盘】浅色模式下标题不可见、整页白底叠白卡
------------------------------------------------------------------------
问题：
  - 系统颜色选「浅色」时，仪表盘顶部「仪表板」三个字是白色，几乎看不见；
    切到「深色」反而正常。
  - 浅色模式下卡片与页面背景几乎没有层次，整个容器呈一片白。

原因：
  - DashboardPage.css 在 :root 里写死了一套浅色调色板（白卡片、深色文字），
    完全不响应 html[data-theme]，深浅两种模式用的是同一组颜色。
  - .header-title 写死 color: #ffffff !important。该 !important 是为了压过
    App.css 的 .content-area h1 { color: #f8fbff }，结果连 AppSettings.css
    的浅色覆盖一起压掉了，浅色模式下就成了白底白字。

现在：
  - 建立完整的令牌体系：:root 放浅色值，html[data-theme='dark'] 整组替换
    为深色值。表面、文字、边框、阴影，以及徽章 / 图标底 / 日历今天与选中
    / 置顶行所用的语义色，全部改为引用令牌。
  - .header-title 改用 var(--text-main)。保留 !important 以确保仪表盘对
    自己标题的控制权，但取值本身跟随主题。
  - 补两处原本只在一种模式下成立的样式：搜索框没写 background / color，
    深色下会是浏览器默认的白底；日历浮层原用半透明底，深色下底层内容会
    透上来，改用不透明的 --bg-elevated。
  - 浅色模式的边框与阴影加深一档（--border-color 从 #e2e8f0 到 #dbe3ee），
    解决卡片与背景无层次的问题。
  - 深色模式下卡片改为与 App.css --surface 对齐的暗色表面，与其他页面一致。

  src/renderer/pages/Dashboard/DashboardPage.css

10. 【会话记录】智能体的问答不会出现在「最近会话」
------------------------------------------------------------------------
问题：
  - 点最近会话旁的加号新建会话，发送内容并得到回答后，该会话始终不出现
    在「最近会话」列表里。

原因：
  - 对话工作台有两条发送路径，只有一条会写会话记录。
  - 普通模式：page.ask() → AskAI:ask，主进程建会话、写入 user 与 assistant
    两条消息、更新 updated_at，渲染层随后 loadConversations() 刷新列表。
  - 智能体模式：runAgent() → Agent:start，AgentOrchestrator 跑工具循环并把
    答案以事件流回渲染层，全程不接触会话仓储，一条记录都没有创建。
  - 因此不是列表没刷新，是根本没有落库。

现在：
  - AskAIService 新增 recordTurn()：把已经生成好的一轮问答写进会话记录，
    不调用模型。没给会话 id 就用问题首句建会话，写入一问一答，挂上的笔记
    记为来源（去重），更新 updated_at。
  - 配套新增 AskAI:recordTurn IPC 与 preload 桥接。
  - 渲染层监听 agent.turns，出现新一轮就落库并刷新最近会话。用 useRef 的
    Set 记住已落库的轮次 id，先登记再落库，避免重渲染或 StrictMode 下重复
    写入；失败后从 Set 中移除以允许重试。
  - 记住返回的会话 id，后续追问追加到同一个会话，而不是每轮新建一条；
    新建会话与切换笔记时清空该 id。

11. 【门禁页】容器重叠、检测时机过早、缺少加载反馈
------------------------------------------------------------------------
问题一（容器重叠）：
  - 门禁页外面又套了一层大容器，与外层内容区重叠，观感冗余。
  - 原因是 .studio-gate 照抄了 .studio-page 的边框、背景与阴影，而外层
    .content-area 已经是一层，加上内部卡片一共三层。
  - 现在 .studio-gate 只保留居中职责，边框、背景、阴影全部去掉。

问题二（检测时机）：
  - 有时门禁提示某些模型未就绪，但进模型管理页显示全部正常，返回后门禁
    又自行消失。
  - 原因是 Runtime:getStatus 与 Semantic:getStatus 都是纯读取，不会启动
    Ollama。应用刚启动时服务器尚未运行，languageModel.serverRunning 与
    embedding.serverAvailable 必然为 false，于是 LLM 与 Embedding 被误判
    为未就绪；而模型管理页读取 LLM 列表时顺手调用了 ensureRunning()，
    服务器被拉起，返回后判定自然通过。
  - 现在新增 Runtime:getReadiness，先 ensureRunning() 再读状态，一次往返
    同时返回运行时与 embedding 两份状态；启动失败不抛错，让检查如实报告
    未就绪而不是整体失败。
  - 另加 20 秒超时上限：Ollama 若卡住，门禁页不会永远转圈，超时后按当前
    状态如实判定，用户仍可看到清单与入口。

问题三（缺少加载反馈）：
  - 进模型管理页需要等待若干秒才显示内容，期间界面一片空白。等待的实质
    就是在启动本地模型服务。
  - 现在门禁检测期间显示转圈与说明文案；模型管理页新增 initialLoading，
    首屏拉起服务与读取四类模型列表期间显示同样的加载面板，列表用 hidden
    隐藏而非卸载，避免加载完成时闪烁。
  - 转圈样式 .app-spinner 与 .app-loading-panel 放入 App.css 作为通用件，
    两处共用，并为 prefers-reduced-motion 降速。

12. 【IPC】Runtime:getReadiness 返回未决 Promise 导致克隆失败
------------------------------------------------------------------------
问题：
  - 门禁页报错：Error invoking remote method 'Runtime:getReadiness':
    Error: An object could not be cloned. 模型管理页显示全部就绪，工作台
    仍被挡住。

原因：
  - RuntimeStatusService.getStatus() 是 async 方法。原有的
    Runtime:getStatus 处理器直接返回该 Promise，ipcMain.handle 会自动
    await 顶层返回值，因此一直正常。
  - 上一节新增的处理器把它放进了返回对象里：
      return { runtime: runtimeStatusService.getStatus(), embedding: ... }
    ipcMain.handle 只 await 最外层，不会递归处理嵌套的 Promise，结构化
    克隆遇到未决 Promise 直接失败。
  - 检查一旦失败，按第 9 节「查不到状态就不放行」的策略挡住整页，因此
    显示的是这条报错而非五项清单。

现在：
  - 改为 Promise.all 先 await 两个状态再组装返回值。
  - 该问题由本次改动引入，非仓库基线问题。

涉及文件：
  src/main/ipc/runtime-ipc.ts
