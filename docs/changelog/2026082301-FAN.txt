贯穿本次改动的四条原则：

  1. 一份内容只生成一次。
     录音完成后不再先生成一份 summary、进入工作空间后再生成另一份
     Structured Note。现在以结构化笔记为唯一结果，复核弹窗只读取其中
     的 summary，保存时整份结构化结果一起落库。

  2. 用户看得到的笔记内容，也必须搜得到、导得出、能作为 AI 上下文。
     标题、转写、结构化笔记和场景知识不再各走一套残缺链路。

  3. 响应式布局通过重新分配空间解决，不允许面板互相覆盖。
     窄屏可以缩侧边栏、笔记栏、输入按钮和关联笔记标签，但当前笔记
     面板始终保持在对话区右侧，不用重叠假装“放得下”。

  4. 删除必须可恢复，清理必须有证据。
     产品内普通删除统一进入回收站；工程文件只有在确认无引用、已合并、
     可重新生成或明确属于旧模板时才删除。

1. 【缺陷】滚动列表后「类型」表头被向上推走
------------------------------------------------------------------------

问题：
  仪表盘的笔记列表有「置顶 / 笔记标题与概览 / 类型 / 发布日期」等列。
  列表内部滚动时，部分表头没有处在统一的 sticky 层中，「类型」两个字
  会先被推走，后面的单元格内容继续顶上来，视觉上像是表头错列。

修复：
  - 表头与列表继续使用同一个内部滚动容器。
  - 表头单元格统一 sticky 定位、top、z-index 和不透明背景。
  - 类型列不再单独脱离表头层级，也不会被正文内容覆盖。
  - 保留原有列宽与筛选交互，不重新引入额外排序控件。

第二段  转写 → 结构化笔记 单一流水线
========================================================================

------------------------------------------------------------------------
2. 【流程】转写完成后直接生成 Structured Note
------------------------------------------------------------------------

旧流程的问题：
  转写完成后先做 summary，保存笔记；用户进入工作空间后，再手工触发
  Structured Note。结构化笔记内部本来就有 summary，这等于相同内容
  调用两次模型、存两套结果，还会出现两份摘要不一致。

新流程：
  1. 音频录制或文件转写完成；
  2. 直接调用结构化笔记生成；
  3. 从同一份结构化结果读取 summary，显示在录音复核弹窗左侧；
  4. 用户确认保存时，转写、summary 和完整 Structured Note 一起落库；
  5. 之后进入工作空间或对话工作台，只读取数据库已有结果，不再要求
     用户手工“重新生成”。

这样 summary 不再是另一条独立 AI 链路，而是 Structured Note 的一个
视图。重新生成仍可作为用户明确触发的更新操作，但不再是首次查看的
必要步骤。

3. 【兜底】短转写和寒暄也必须有结构化输出
------------------------------------------------------------------------

问题：
  录音内容只有「你好 你好 你好 你好」时，转写本身已经成功，但复核弹窗
  显示「暂无结构化摘要」。这把“内容简单”错误地处理成“没有内容”。

修复：
  - 只要存在非空转写，就生成最小可用的结构化结果。
  - 模型没有返回受支持 summary 时，解析层根据转写生成可读兜底摘要。
  - 关键要点、任务、提醒等字段允许为空，但整份结果不能因此消失。
  - 真正的空转写仍按空内容处理，不凭空编造信息。

结果：
  「你好」类短音频也会得到与原文相符的摘要 / 要点，而不是错误提示。

5. 【排版】长标题不再一个单词占一行
------------------------------------------------------------------------

问题：
  当前笔记标题较长时，例如
  “Next Standup Meeting Attendance Confirmation”，右侧详情面板明明仍有

  - 日期和关闭按钮仍保持在标题区右上角，不挤压正文为极窄列。

同时删除详情内重复的「结构化笔记」总标题。用户已经处在当前笔记详情，
下面直接显示「摘要 / 关键要点 / 任务与行动计划」即可，不再重复说明一次。

10. 【自定义模板】用户需求先由本地模型规范化
------------------------------------------------------------------------

问题：
  用户输入的模板需求可能口语化、重复、含糊，直接当提示词保存会导致
  输出结构不稳定；但要求用户自己学习 prompt engineering 也不合理。

实现：
  - 用户填写名称、用途和希望保留的信息。
  - 保存前调用当前本地 LLM，把需求整理成稳定的 Scenario Knowledge：
    清楚描述提取目标、输出分区、边界和不应编造的内容。
  - 保存原始需求和规范化结果，方便后续编辑与审计。
  - 模型不可用或输出无法解析时返回明确错误，不静默保存半成品。
  - 自定义模板带「自定义」标记，与 SpeakSpace 维护的内置模板区分。
  - AI 规范化所用语言跟随系统语言，不再随机中英文混用。

17. 【导出】Word / PDF 包含完整 Note
------------------------------------------------------------------------

旧问题：
  下载后的 Word / PDF 只有标题、转写或少量摘要，和工作空间实际展示的
  笔记内容不一致。

实现：
  导出先构造统一 NoteExportData，再分别渲染 Word 与 HTML/PDF。
  导出内容包括：
  - 标题、工作空间、创建 / 更新时间等元数据；
  - 原始转写；
  - Structured Note 的全部分区；
  - Scenario Knowledge 的全部分区与模板来源；
  - 任务完成状态、提醒和日程；
  - AI 输出中属于当前笔记的持久化内容。

排版：

19. 【TTS】短句切分 + 播放时预生成下一段
------------------------------------------------------------------------

问题：
  LLM 回答已经很快，但整段文本一次送给本地语音模型时，首段音频要等
  全文推理结束后才播放，主观等待明显。

实现：
  - 长文本按自然标点切成约 24–40 个字符的短句。
  - 优先使用句号、问号、感叹号和分号作为强边界；找不到时再用逗号、
    冒号或空格；最后才按最大长度硬切。
  - 第一段生成后立即播放，不等待后续全文。
  - 播放当前片段时并行合成下一片，把大部分推理时间藏在播放时间里。
  - 保留取消检查；停止播放后，不继续播放已经在后台完成的下一段。
  - 第一段音频 ready 时就更新 UI 状态，用户更早得到反馈。

这不会改变语音模型本身的算力需求，但显著缩短“点播放到第一次出声”的
体感时间，并降低长文本推理时间非线性增长带来的卡顿。
