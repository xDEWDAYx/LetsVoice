1. 【BUG-001 / P1】提取失败时把私人 LLM 输出写进 console
------------------------------------------------------------------------
问题：
  报告只点了两处 console.warn / console.error 带 content 的问题，
  实测确认存在，另外还发现两处报告没覆盖的泄漏：

  a. 报告指出的两处（TodoExtractionService.ts:152 / :168）
     解析失败时把整段 LLM 输出传给 console，而 LLM 失败时输出的
     往往正是笔记原文的复述。

  b. JSON.parse 的报错信息本身带原文
     V8 的 "Unexpected token 'I', \"I found th\"... is not valid JSON"
     会把出错位置附近的原文一起吐出来。所以连 error.message 都不能
     直接给 console。

  c. 外层 catch 的 console.error(..., error)
     Ollama 报错时可能回显整个 prompt，而 prompt 里内嵌笔记全文。

修复：
  - 新增静态方法 log / sensitivePreview / errorKind / errorDetail。
  - console 只留 note id、输出长度、错误类型名。
  - 原文一律走 debugOnly 日志，且截断到 2000 字并加
    「[SENSITIVE — debug only]」前缀。
  - 顺手修掉报告提到的 :55 空白与 :61 未使用的 catch 变量
    （改成 ES2019 的可选 catch 绑定）。

  另外把日志落点改成可覆盖：
    SPEAKSPACE_LOG_DIR 优先，否则才用 app.getPath('userData')。
    排障时能把日志导到指定目录，测试也不必再依赖 Electron 替身。
    （这一条同时解决了一个测试偶发失败，见第四段。）

测试：src/__tests__/TodoExtractionService.privacy.test.ts（4 项）
  覆盖非 JSON 输出、JSON 解析失败、上游报错回显 prompt，
  以及「显式打开 debug 时原文只进日志文件、仍不进 console」。

第二段  模型输出的富文本渲染
========================================================================

问题：
  维护者反馈「模型生成的文本老是带星号」。核实结论：**完全没做过**。
  全应用没有任何 Markdown 渲染，所有 AI 输出都走 <p>{text}</p>，
  所以 **加粗** 原样显示成星号。

  佐证这不是疏忽而是缺口：
    renderer/tts/TTSContent.ts 里有 toSpeechText()，朗读前专门去掉
    Markdown 标记；main/workflow/StructuredNoteSupport.ts 更是直接
    要求模型「按模板输出 Markdown」，contentType 写死 'text/markdown'。
    也就是说全链路都知道模型在输出 Markdown，唯独没人渲染。

实现选择（先试了库，实测后放弃）：
  先装了 react-markdown ^10 + remark-gfm ^4，实测 Jest 直接崩：
    SyntaxError: Unexpected token 'export'
  这条依赖链是纯 ESM，ts-jest 要为几十个包
  （unified / micromark-* / mdast-* / hast-* …）配 transformIgnorePatterns，
  脆弱且拖慢每次测试。权衡后卸掉，自己写。

新增 src/renderer/components/Markdown/
  markdownAst.ts    纯解析，产出 AST，无任何 DOM 依赖
  MarkdownText.tsx  只输出 React 元素，全程不碰 dangerouslySetInnerHTML
  MarkdownText.css  只用 tokens.css 的语义变量，明暗主题自动跟随

  支持：**粗** / *斜* / ***粗斜*** / ~~删除线~~ / `行内代码` /
        围栏代码块（含语言标记）/ 标题 / 有序无序列表 / 嵌套列表 /
        任务列表 / 引用块 / 分隔线 / GFM 表格（含列对齐）/ 链接 / \* 转义

  安全性由结构保证：只产出 React 元素，笔记里混进的
  <script> / <img onerror> 只会显示成字面量；链接只放行
  http(s) / mailto / 相对路径，javascript: 一律降级为纯文本。

接入的 8 处（只渲染模型产出，用户自己敲的内容保持纯文本）：
  Studio 对话与智能体回答      StudioChatPanel.tsx
  AskAI 对话                   AskAIChatPanel.tsx
  Agent 页对话                 AgentConversation.tsx
  知识模板产出                 KnowledgeOutputPanel.tsx
  笔记摘要 / 子笔记            AskAINotePreview.tsx、WorkspaceNoteCard.tsx
  多笔记问答弹窗               WorkspaceMultiNoteModal.tsx
  实时语义整理                 TranscriptionPanel.tsx
  录音复核弹窗                 RecordingReviewDialog.tsx

  刻意不渲染：用户输入的问题、语音转写原文。
  那两类不是模型推理产出，按 Markdown 渲染会把「星号就是星号」的
  文本弄坏。TTS 与复制按钮继续拿原始文本（朗读自己会去标记，
  复制应该给出 Markdown 源码）。

一处必须记下的坑：
  各页面早有 `.content-area p`、`.ask-ai-messages article p`、
  `.workspace-content-item p` 这类后代选择器，权重和组件自身的
  `.markdown-body p` 相同甚至更高，谁生效取决于打包顺序 ——
  富文本段落会在某些页面变灰、或被塞进额外行距。
  解决办法是在 MarkdownText.css 内部用重复类名把权重抬到 (0,3,x)，
  只改组件自己这一个文件，不动各页面既有排版。

  另有两处结构变动必须同步改宿主 CSS：
    存档对话的栅格原本挂在 p 上 → 改挂 .workspace-conversation-message
    .live-summary__segments li > span:last-child 因 span 被替换而失配
    → 选择器补上 li > .markdown-body

测试：markdownAst.test.ts（27 项）+ MarkdownText.test.tsx（9 项）
  含 XSS 三连（script / img onerror / javascript: 链接）
  与「纯口语转写不会凭空多出标记」。

第三段  待办提取的日期解析重做
========================================================================

这一段是本次投入最大的部分，起点是维护者实测：
「周五之前……下周一……八月三十一号」三个日期，只有 8/31 出来了，
反而凭空多出一个今天。

------------------------------------------------------------------------
3.1 根因（三条，互相独立）
------------------------------------------------------------------------
  a. 只给日期不给星期
     prompt 里只塞了一个 `2026-08-20`。模型无从知道那天是星期四，
     「周五」「下周一」根本没法算，只能退回它唯一见过的那个日期
     —— 也就是今天。用户看到的「凭空多出今天」就是这么来的。

  b. toISOString() 是 UTC
     东八区用户在早上八点前，取到的是前一天，整条时间线差一天。

  c. item.dueDate || today
     模型返回 null 时静默记成今天，且不留任何日志。
     「不知道」和「今天到期」在库里无法区分。

------------------------------------------------------------------------
3.2 DateContext.ts —— 日期基准
------------------------------------------------------------------------
  toLocalDateString()  本地时区取日，替换掉所有 toISOString().split()
  buildDateReference() 预先算好 26 行对照表塞进 prompt：
                       今天/明天/后天/大后天/昨天、本周一~本周日、
                       下周一~下周日、本周末、一周后、两周后、
                       本月底、下月初、一个月后
                       并写明「查表，不要自己算」
  normalizeDueDate()   落库前校验：必须是真实存在的日历日期
                       （用往返比对挡掉 2026-02-31 这类会被 Date
                        静默进位的值），年份限制在 [今年-1, 今年+5]

  测试：DateContext.test.ts（19 项）

------------------------------------------------------------------------
3.3 RelativeDateRewriter.ts —— 就地标注（核心思路）
------------------------------------------------------------------------
  只给对照表还不够：模型在长文本里懒得回查，「周五之前」照样解析不出。
  维护者提出「在 summary 阶段直接把词换成日期」，方向对，但两点需要调整，
  实现时都做了修正：

    其一，summary 不是被提取的对象。
      StudioPage 保存时 transcript 与 summaries 是两个独立字段，
      extractTodosForNote 读的是 transcript。改 summary 完全不影响提取。

    其二，不能交给模型做替换。
      模型算不对「周五」，在 summary 阶段同样算不对，
      只是把同一个错误挪早一步，还多一个失败点。

  最终做法：纯规则改写，在文本送进模型之前把答案写在词的旁边。
    「周五之前交」→「周五(2026-08-21)之前交」

  保留原词 + 补注日期，而不是直接替换：规则判错时原话还在，
  模型还有纠正余地，待办标题也不会丢掉语气。
  只改送进模型的副本，落库的转写原文一个字不动。

  覆盖范围（分四批加进去，每批都对应一次实测反馈）：
    第一批 相对日期  今天/明天/后天/大后天/昨天/前天
                     周X / 星期X / 礼拜X / 周5（语音转写会出数字）
                     本周X / 这周X / 下周X / 下下周X / 上周X
                     月底 / 下月初 / 下个月 / 周末
                     N天后 / N周后（中文数字与阿拉伯数字都认）
                     today/tomorrow/next Monday/this Friday/in 3 days
    第二批 绝对日期  八月三十一号 / 8月31号 / 9月4日 / 十二月二十五号
                     2027年3月14日 / 二零二六年八月三十一号
                     （维护者实测 8/31 失效就是因为这批当时没做，
                       模型自己换算中文数字失败后回落到今天）
    第三批 区间与周期 上旬(取10号) / 中旬(取20号) / 下旬(取月末)
                     年底 / 年末 / 年初
                     每天 / 每日 / 每个工作日 / 每周X / 每两周 /
                     每月X号 —— 标成 (首次日期, REPEAT=类型)
    第四批 相对基准  提前N天 / 提前一周 —— 基准是**同句里前一个日期**，
                     所以必须等第一遍标完再跑第二遍扫描。
                     「九月十号(2026-09-10)要汇报，提前三天提醒我」
                       → 「…提前三天(2026-09-07)提醒我」
                     找不到基准就不标，不拿今天硬凑；跨句不借用。

  三条刻意的克制：
    - 裸「三号」不匹配。必须带「月」和「号/日」才算数，
      否则「三号楼会议室」「三号线」会被误标，代价远大于收益。
    - 不存在的日期不标注（二月三十号 / 13月1号）。
    - 单次扫描：全部规则合并成一条大正则，保证「下周五」被整体消费，
      内部的「周五」不会再被裸规则匹配一次。

  一处语义调整（维护者两次指出后采纳）：
    裸「周X」原本是「本周还没过就算本周」，于是周四说「周四之前」
    落在今天。改为「当天算已过，顺延到下周」——
    今天已经过了大半，当截止日没有意义；口语里「周四见」在周四当天说
    通常也是指下一个周四。
    「本周四」写明了本周，不适用顺延，仍是今天。

  测试：RelativeDateRewriter.test.ts（57 项）

------------------------------------------------------------------------
3.4 RecurrenceExpander.ts —— 重复待办逐次展开
------------------------------------------------------------------------
  维护者要求：「只要是重复任务，每次重复都要在日历上标出来」。

  原先的 prompt 规则写的恰恰相反（「emit ONE task…not one per
  repetition」），所以「每周五」只在第一个周五出现过一次。规则已反转。

  展开放在代码里而不是让模型逐条输出：
  「每天」半年就是 180 条 JSON，小模型必然中途跑偏或截断。
  模型只负责给出「起点 + 周期类型」，日期推算是确定的。

  展开窗口（都是命名常量，好改）：
    daily / weekdays  90 天      weekly / biweekly  182 天
    monthly           365 天     单条上限 120 次
  每月按「同一号」推进，遇到 2 月没有 30 号直接跳过该月，
  而不是滑到下月 1 号。

  测试：RecurrenceExpander.test.ts（12 项）

------------------------------------------------------------------------
3.5 CompletionDetector.ts —— 已完成的事不该变成待办
------------------------------------------------------------------------
  「服务器的续费上周就办好了」会被抽成「续费服务器」，
  又因为没有日期回落到今天 —— 上周就结束的事出现在今天的日历上。
  提示词改了四版都压不住，改成规则判定。

  两级处理：
    1. 逐句标注「(已完成)」，把信号放到词的旁边；
    2. 整段都是已完成时直接短路，连模型都不问，直接零待办。

  判定收得很紧：只认明确的完成标记（已经…了 / …完了 / …好了 /
  都结了 / 搞定了 / already / done …），不认光秃秃的「了」。
  「把墨盒换了」是待办不是完成，误判会整条吞掉真待办。

  测试：CompletionDetector.test.ts（15 项）

------------------------------------------------------------------------
3.6 落库环节的三处加固
------------------------------------------------------------------------
  a. 重复条目去重
     标题 + 日期完全相同的必然是同一条（小模型会把同一件事输出好几遍）。

  b. 周期必须有据可依
     模型看到「周五」就自己脑补 weekly，把一次性任务铺成 27 条。
     现在只认文本里真出现过的 REPEAT=xxx，没标注过就一律置空。
     （实测日志：Dropped ungrounded repeat "weekly" for "周五负责客户接待"）

  c. 日期兜底顺序 + 日志
     模型漏抄 dueDate 时，若全文只标注了一个日期，就用那个；
     有多个才回落今天。并且**每次兜底都写日志**：

4.4 TodoOwnershipFilter.ts —— 归属复核（维护者提出的两步判断）
------------------------------------------------------------------------
  维护者的判断是对的：抽取那一步要模型同时做五件事
  （找任务、判归属、判完成、抄日期、定周期），11 条规则，
  3B 模型顾此失彼；而反复失手的恰恰是筛选，不是抽取。
  拆成「只问一件事」的第二步是正确方向。

  但按原样实现会出事，实测数据：
    「这个报价我来跟，物流那块让小刘去对接」
      → 1|OTHER_PERSON 2|MINE     判反了
    「客户那边还等着我们的报价呢」
      → 1|OTHER_PERSON            这明明是自己的活
    correctDrops=2  falseDrops=2  —— 五成误删率

  它还把「周五之前把季度报表发给财务」判成 ALREADY_DONE、
  把「更换打印机墨盒」判成 NOT_A_TASK。
  风险不对称：多留一条用户划掉就行，误删是真丢事情。

  最终方案 —— 模型判断前面加一道确定性闸门：
    只有转录里出现明确甩手表述（我就不管 / 不归我管 / 不用我管 /
    跟我没关系 / 我不参与 …）才允许据此删除；
    没有这句话连第二次模型调用都不发。

    并且只采信 OTHER_PERSON 一类。ALREADY_DONE / NOT_A_TASK
    照样收集、照样记日志，但绝不据此删除 —— 实测这两类误判率太高。
    等换上更大的模型后重跑评测，可以再考虑放开。

  加闸门后实测：
    6/6 全对，falseDrops=0，且 6 条里只有 1 条需要发第二次模型调用。

  四道保险（都有测试覆盖）：
    复核报错          → 原样返回全部候选
    某行解析不出来    → 该条保留
    ≥4 条全被判丢     → 视为模型塌缩，整批保留
    没有甩手表述      → 根本不跑复核

  测试：TodoOwnershipFilter.test.ts（14 项）

第六段  Agent 模式：分层提示词与有界循环
========================================================================

维护者要求把 Agent 的提示词做成有层级、作用域、优先级的结构，
并把工具结果回灌形成完整循环。

先说清楚现状核对：**工具结果回灌本来就有**。
每轮 tool 消息都会回到上下文，模型下一轮能读到。这部分原本就是对的。
缺的是结构与收敛。

原先的问题：
  - 系统提示词是一整段没有结构的话（约 90 词），规则平铺，
    冲突时模型无从裁决。
  - 循环没有自我感知：模型看不到还剩几步、已经调过什么，
    于是可以把 search_notes("物流") 连发六次直到撞上限。
  - 撞上限返回一句模板话「已达到 6 步安全上限」，而不是真答案。

新增 src/main/agent/AgentPrompt.ts —— 六层提示词：

  L0  ROLE           全程
  L1  INVIOLABLE     不得编造 id / 内容 / 日期 / 工具结果；不泄露推理
  L2  TOOL PROTOCOL  每轮至多一个工具；只用真实 id；不重复同一调用
  L3  LOOP POLICY    先搜再说；每次调用必须能改变答案；预算有限
  L4  OUTPUT         用户语言、简洁、用笔记名而非 id
  L5  SESSION SCOPE  工作区范围、挂上的笔记（优先级最低）

  文首写明裁决顺序：编号小的优先；并明确
  「L5 是上下文不是许可，永远不能压过 L1」。

AgentOrchestrator.ts 三条外部（代码级）约束：

  1. 每轮回灌运行状态
     [RUN STATE] step 2 of 6 · 4 remaining
     Calls already made in this run:
       - search_notes(query="物流")
     模型这才谈得上知道自己在循环的哪个位置。

  2. 重复调用短路
     工具名 + 规范化参数（键排序后比对，所以参数顺序不同也算重复）
     命中则**不再真正执行**，回灌一句「已经调过，用那个结果或直接作答」。
     既省一次工具开销，也把模型从原地打转里拽出来。

  3. 最后一步收走工具
     最后一轮传空工具列表，模型没得可调，只能拿现有信息作答。
     撞上限从「甩一句模板话」变成「给一个真答案」。

  设计原则与全篇一致：提示词负责让模型愿意照做，
  编排器负责模型不照做也不会出事。

实测（真实 qwen2.5:3b-instruct，非 mock）：
  call search_notes → result ok=true → final
  searchCalls=1  completed=true
  答案："在"物流对接安排"这条笔记中，对接人的名字是小刘，
        联系人是顺丰的王经理。"

  测试：AgentPrompt.test.ts（14 项）
        AgentOrchestratorLoop.test.ts（10 项）
        含「模型死循环发同一个调用」也能正常收敛的用例。
