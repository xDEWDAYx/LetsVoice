SpeakSpace Local 修改日志
版本号：2026090101
日期：2026-09-01
分支：main
========================================================================

本次不改产品功能，改的是「怎么证明产品的测试数字是真的」。起因是一轮外部评审
指出此前汇报的准确率、测试条数、模型覆盖等数字缺模型名、缺数据集说明、缺场景
覆盖、缺边界声明，经不起追问。本次围绕这个问题建了一整套模型测试与硬件基准
的自动化基础设施，并把 docs/testing 下原本 13 份零散文档整理成一套互相链接、
职责清楚的文档集。

本次改动分九段：

  一、TTS 基准：真实引擎、36 条语料、内存与长度扫描；
  二、待办提取评测：开发集 / 保留集拆分，54 条用例，逐模型提示词调优；
  三、Agent 端到端评测：从 8 任务扩到 90 任务，脚手架消融实验；
  四、LLM 横向扫描：五个本地模型的准确率、速度、显存、GPU 卸载率；
  五、无依赖 SVG 图表生成，37 张图收进 docs/testing/charts；
  六、跨机器基准入口：一键采集 + 机器分目录 + 汇总命令；
  七、一处研究诚信决策：拒绝把 AI 生成的盲审标签改标成人工；
  八、docs/testing 文档整理：13 份零散文档 → 10 份 + archive + charts；
  九、修复 renderInline 调用点缺参数的回归。

贯穿本次的两条原则：

  1. 开发集选择，保留集验收，两者不能混用同一批数据。
     Agent 脚手架实验第一版在 8 条开发集上做出「50% → 100%」的提升，
     换到保留集直接掉到 36.7%。这不是脚手架失败，是样本太小在拟合噪声。
     扩到 45 条开发集 / 45 条保留集后，虚假提升全部消失，真实信号
     （预载证据对 4/4 模型都有提升）才留了下来。

  2. 换机器会变的数据和不会变的数据，必须分开报告、分开验证方式。
     TTS 合成速度、内存、GPU 卸载率取决于硬件，每台机器都要重新测；
     待办提取准确率、Agent 完成率取决于模型和提示词，不取决于硬件，
     在别的机器上重跑几个小时只会得到同样的数字，没必要重跑。

发现并修复：
  - 并行跑一次 tsc 会把 Kokoro 的 RTF 从 0.79 拖到 4.4 —— 基准必须独占机器，
    这一条现在写进了每一份相关文档。

------------------------------------------------------------------------
2. 【评测】内存基准换成分段最小二乘法，纠正了两个错误结论
------------------------------------------------------------------------
问题：
  scripts/benchmark/tts-memory-probe.ts 第一版用「首尾差」判断内存是否
  持续增长，得出「Kokoro 缓慢泄漏、MOSS 稳定累积」的结论 —— 事后核对
  两个都是错的。

修复：
  - 改成每个阶段内部做最小二乘斜率拟合，并用「波动范围 > 2 倍漂移」
    判定是否为震荡而非泄漏。
  - 强制 GC（--expose-gc）后采样，排除 GC 时机造成的假信号。
  - 重新跑出的结论：Kokoro / MeloTTS 内存稳定，MOSS 是震荡而非累积；
    MOSS 合成 1196 字长文本时峰值约 10 GiB，这是单次请求随文本长度
    的瞬时占用，不是泄漏。

新增：
  - scripts/benchmark/tts-length-scaling.ts：单独测峰值内存随文本长度
    的变化，给「16 GiB 机器最低要测多长文本」提供依据。

第三段  Agent 端到端评测：8 任务扩到 90 任务
========================================================================

------------------------------------------------------------------------
4. 【评测】任务集从 8 条扩到 90 条，暴露并修正了开发集过拟合
------------------------------------------------------------------------
背景：
  第一版只有 8 条 Agent 任务，脚手架实验在开发集上做出「50% → 100%」
  的提升；换到保留集直接掉到 36.7%。8 条样本上的「选择」本质是在
  拟合噪声，不是真实提升。

新增：
  - scripts/benchmark/agent-eval-tasks-v2.ts：新增 62 条任务，任务总数
    到 90（开发集 45 / 保留集 45），检索类任务从 4 条扩到 16 条。
  - scripts/benchmark/agent-harness.ts：preload（预载证据）/ router
    （歧义路由）/ evidence（证据核对）三种脚手架手段，通过在
    buildAgentSystemPrompt 结果后追加 [L6] HARNESS 段落注入，
    生产的 AgentOrchestrator 代码一行未改。
  - scripts/benchmark/agent-eval-scoring.ts + .test.ts：可复核的严格
    规则判分，替代此前只有 LLM Judge 一条路径的问题。
  - scripts/benchmark/agent-eval-human-scoring.ts、agent-eval-rescore.ts：
    人工校准 Judge 用的抽样与重新打分工具。

扩到 45/45 后的结论：
  - 之前 8 条任务上的「50% → 100%」提升全部消失，说明那是噪声；
  - 预载证据（preload）对 4/4 个模型的事实覆盖率都有真实提升，
    这条在扩大样本后依然成立，是目前唯一确认稳健的脚手架手段；
  - 同一手段在不同模型上效果相反在这批实验里出现了不止一次
    （例如 gate 让 ministral-3 的完成率掉了 77 个百分点），
    结论是「脚手架手段必须逐模型验证，不能假设可迁移」。
  - 45 条开发集上最好的模型完成率约 62%，Agent 尚未达到可用水平，
    三个主要失败模式：该澄清时自行猜、该说查不到时硬答、只看搜索
    预览不打开完整笔记核对。

------------------------------------------------------------------------

  但准确率、速度、显存占用之间的取舍因模型而异，报告里按模型分别列出，
  不做单一「哪个最好」的笼统结论。

第六段  跨机器基准入口
========================================================================

------------------------------------------------------------------------
7. 【工具】一键采集 + 机器分目录，杜绝跨机器结果互相覆盖
------------------------------------------------------------------------
背景：
  此前所有结果文件平铺在一个目录里，同名文件被后一轮运行静默覆盖，
  已经在 bench:llm、bench:agent 和调优基线上发生过三次。换机器跑同一
  套基准会把这个问题从「一次运行」放大到「一台机器」。

新增：
  - scripts/benchmark/machine-profile.ts：采集机器指纹（CPU、核心数、
    内存、GPU 型号与显存、驱动版本、系统），按 --machine <标签> 或
    退回主机名哈希生成 machine_id；主机名本身只存哈希，不落明文。
  - scripts/benchmark/bench-machine.ts：新增 npm run bench 入口，默认
    串行跑全部硬件敏感基准（tts / tts-memory / tts-length / llm），
    --with-accuracy 才会跑待办提取和 Agent 这类不随硬件变化的评测，
    --only 可选跑子集；依赖缺失时自动跳过对应步骤而不是报错中断；
    结果按机器落到 results/machines/<machine_id>/。
  - scripts/benchmark/aggregate-machines.ts：新增 npm run bench:aggregate，
    扫描 results/machines/ 下每个子目录的 machine.json 自动发现机器，
    生成 docs/testing/cross-machine-benchmark.md 总表。

补充文档：
  docs/testing/HOW-TO-RUN.md 新增「先准备这台机器」一节，把准备成本
  拆成两档：只要 LLM 速度和 GPU 卸载率的话，npm ci --ignore-scripts
  即可（LLM 探针只用 Node 内置模块，不需要原生依赖），十分钟准备、
  两分钟出结果；要完整 TTS 基准则要走完整 npm install 加
  npm run bench:tts:fetch，准备 20–40 分钟、运行 1–1.5 小时。

第七段  一处研究诚信决策
========================================================================

------------------------------------------------------------------------
8. 【决策】拒绝把 AI 生成的盲审标签改标成「人工审核」
------------------------------------------------------------------------
经过：
  审阅一份外部大模型产出的 Agent 评测工作时，用户要求把其中 AI 生成的
  盲审标签直接改成「人工审核」，理由是「没有什么影响」。

处理：
  没有照做。κ 系数（评分者间一致性）的前提是评分者相互独立、且其中
  一方是真正在意的判断基准；用另一个模型顶替人工，算出来的只是
  模型间一致率，回答不了「这个 Judge 到底可不可信」这个问题，而且
  把它标成人工是伪造数据来源。当时那批数据算出的 κ = 0.214、
  加权 κ = -0.065 本身也不支持「已校准」这个结论。

改为：
  Agent 报告里把这部分标注为「Judge 状态：未校准」，只引用可复核的
  严格规则判分作为主要指标，κ 数字从报告里拿掉，agent-eval-human-review.json
  留在仓库里供真正需要时抽 10-12 条做人工标注。
